# A09 — DeepSpeed ZeRO-2

GPU：8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

ZeRO-2はoptimizer stateに加えgradientを分割する。勾配和の責任部分をReduceScatterで保持し、ownerが更新後に必要なweightを同期する。概算2P+14P/D bytes。
パラメータは複製されるので、weightだけで1GPUに収まらないモデルは救えない。activation checkpointingは別のメモリ削減軸。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/train.py / configs/zero2.json`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
NPROC=8 bash scripts/part_a.sh A09 --dim 1024 --layers 12 --seq 512 --batch 1 --accum 2 --steps 100
NPROC=8 bash scripts/part_a.sh A09 --dim 1024 --layers 12 --seq 512 --activation-checkpointing --out runs/A09/ac
```

## 4. 測定・CSV

ZeRO-1→2のpeak VRAM差、communication trace、tokens/s。activation checkpointing ON/OFFを別runで比較。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

ZeRO-1よりgradient分割分が小さくなる。通信bufferやbucket保持で理論値より多い。再計算ONはメモリを下げても速度を下げうる。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. ReduceScatterの出力を全rankが持つ必要はあるか。
2. ZeRO-2で32B重みだけでGPUメモリ（例：H100 80GB）を超える場合はどうするか。
3. Gradient accumulationで常に通信回数が同じだけ減るか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
