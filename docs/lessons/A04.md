# A04 — NCCL通信ベンチマーク

GPU：2〜8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

AllReduceは全rankの和を全rankへ、AllGatherは断片を全rankへ、ReduceScatterは和の断片を各rankへ配る。実装はrank+1の値を用いて期待値D(D+1)/2を検証してから時間を測る。
AllReduceのbus bandwidth=algorithm bandwidth×2(D−1)/D。AllGather/ReduceScatterは×(D−1)/D、Mの定義はAllGatherで集約後サイズ、ReduceScatterで入力全体サイズ。本CSVのbytesはこのM。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/collectives.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
for n in 2 4 8;do
 NPROC=$n bash scripts/part_a.sh A04 --iters 50 --max-power 28 --out runs/A04/${n}gpu.csv
done
```

## 4. 測定・CSV

bytes、latency_ms、algorithm_GBs、bus_GBs。小メッセージのlatencyと大メッセージの帯域を分けてプロットする。NCCL_DEBUGログのRing/Treeやチャネルも確認。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

小メッセージはlatency支配、大きいメッセージは帯域が飽和へ近づく。NVSwitch内とEFAノード間で差が出る。3種Collectiveのbytes定義が違うことを確認する。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. 32KiBと256MiBで同じ帯域にならない理由は何か。
2. AllReduceとReduceScatter＋AllGatherが近い理由は何か。
3. bus_GBsを物理リンク速度とそのまま比べてよいか。
