# A06 — Data Parallelismの手動実装

GPU：2〜8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

同じ初期パラメータをbroadcastし、rankごとに別データの平均lossを求める。各パラメータ勾配をAllReduce SUM後、Dで割る。全rankが同じAdamW更新をすると同じモデルを維持できる。
Accumulationを使う場合はloss/aでbackwardし、a micro-step後に平均勾配同期する。本教材は同期型で、パラメータごとのAllReduceを直列に行い、bucket化とoverlapを敢えて見せていない。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/train.py：manualモード`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
NPROC=2 bash scripts/part_a.sh A06 --steps 100 --accum 2 --out runs/A06/manual2
NPROC=8 bash scripts/part_a.sh A06 --steps 100 --accum 2 --out runs/A06/manual8
```

## 4. 測定・CSV

rank別loss/step_s/VRAMと保存後のモデル重みを比較。Profilerでbackward終了後に細かいAllReduceが並ぶことを調べる。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

rankごとのモデルは一致する。平均を忘れると学習率をD倍したような更新になる。小さいparameter多数の通信はlatencyで遅くなりやすい。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. SUMをDで割らないとどうなるか。
2. 各rankの初期重みが違う場合、勾配同期だけで同じモデルになるか。
3. 勾配を1個のbufferへまとめれば何が改善するか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
