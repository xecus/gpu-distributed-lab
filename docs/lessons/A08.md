# A08 — DeepSpeed ZeRO-1

GPU：8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

ZeRO-1はoptimizer state（FP32 masterとAdamのm/v）をrank間で分割する。weightとgradientは複製。概算state memoryは4P+12P/D bytes、BF16 weight/gradの仮定。
engine.backwardとengine.stepを各micro-stepで呼び、更新境界はDeepSpeedがaccum設定に従い管理する。native loopのloss/aとengine側のscalingを二重適用しない。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/train.py / configs/zero1.json`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
NPROC=8 bash scripts/part_a.sh A08 --dim 1024 --layers 12 --seq 512 --batch 1 --accum 2 --steps 100
# まず小さいモデルでengineとcheckpointの受け入れ
bash scripts/acceptance.sh
```

## 4. 測定・CSV

DDPと同じ条件のper-rank peak VRAMとstep_s、DeepSpeed logのstage、dtype、train batchを確認。optimizer first step後を含むピークを使う。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

大きいPのモデルではoptimizer stateの分割分だけVRAMが減る。tinyモデルでは通信bufferやランタイムが相対的に大きく、単純な1/8削減にはならない。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. AdamWのm/vが重みより大きい理由は何か。
2. 全rankでoptimizerを丸ごと保持する無駄はどのくらいか。
3. ZeRO-1でactivationメモリは減るか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
