# A05 — 自作Ring AllReduceとNCCL比較

GPU：2〜8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

各rankは全ベクトルをD分割し、隣接rankへsend/recvする。ReduceScatterのi回目で送るchunkは(r−i) mod D、受けるchunkは(r−i−1) mod D。D−1回で自分が責任を持つ和が完成する。AllGatherをさらにD−1回行い全chunkを揃える。
通信量は1rankあたり2(D−1)M/D。batch_isend_irecvの非同期ペアとwork.waitで循環するblocking sendのdeadlockを避ける。NCCL組込みAllReduceとの数値比較を最初に行う。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/ring.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
NPROC=2 bash scripts/part_a.sh A05 --elements 1048576 --iters 20
NPROC=8 bash scripts/part_a.sh A05 --elements 67108864 --iters 20 --out runs/A05/ring8.csv
```

## 4. 測定・CSV

ring.csvのimplementation、latency_ms、bus_GBs。rankごとのsend/recv chunk indexを紙または図で追う。ネットワーク遅延、Python処理、追加bufferの影響も分析する。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

結果は浮動小数加算順の誤差範囲で一致する。自作RingはPython/P2P overheadと最適化不足でNCCLより遅い傾向。worldで割り切れる要素数に調整している。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. ReduceScatter終了時、rank rはどのchunkの和を持つか。
2. sendとrecvを順番にblockingで書くと何が起こるか。
3. 数値bit一致しないことは必ずしもバグか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
