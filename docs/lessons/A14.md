# A14 — Profiler・MFU・Scaling Efficiency

GPU：1〜40。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

MFU近似=(6P×tokens/s)/(GPU数×BF16 dense peak)。モデルが有効に使った演算の比率で、GPU utilizationとは違う。Activation再計算やoptimizerは6P式に入らず、VLAには同じ式を使わない。
Strong efficiency=(Tbase/TD)/(D/Dbase)。NCCL kernelの時間は演算と重なり、kernel時間和をstepから差し引いて露出通信とするのは誤り。タイムラインでidle gapを見る。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`scripts/trace_stats.py / scripts/summary.py / scripts/scaling.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
python scripts/trace_stats.py runs/A14/trace_rank0.json --out runs/A14/trace_stats.csv

```

## 4. 測定・CSV

Profilerは1updateを別計測。通常runのmedian/p95 step、全rank peak、CUDA NCCL区間和、GEMM/idle、USD/1M tokensをまとめる。Scalingには各runのsummary.jsonを使う。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

small model/strong scalingでは通信・launch overheadがMFUを下げる。Weak scalingではGEMMを大きく保ちやすい。速いtokens/sでもUSD/1M tokensが悪化する場合がある。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. Utilization90%なのにMFU20%となる可能性はあるか。
2. 通信と演算を重ねると通信durationは減るか。
3. 追加GPUを買う判断にtokens/s以外の何を使うか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
