# A03 — GPU数とBatch Size・Gradient Accumulation

GPU：1〜8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

G=b×a×D。GPU数Dを増やすとき、aを減らせばGを固定できる。gradient accumulationはmicro lossをaで割って勾配を蓄積し、Adam更新をa回に1回行う。DDPのno_syncで最後のmicro-step以外のAllReduceを省く。
Strong scalingはglobal batch16を固定、Weak scalingはbatch1/accum2を固定する。異なるGではoptimizer更新数が同じでも処理token数が違うため精度比較に注意する。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`scripts/batch_sweep.py / lab/train.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash

# まず1条件だけ確認する例
NPROC=4 bash scripts/launch.sh lab.train --mode ddp --batch 1 --accum 4 --sampler --out runs/A03/strong_4gpu
```

## 4. 測定・CSV

各strong_Ngpu/weak_Ngpuのglobal_batchを確認。CPUサンプル生成やH2Dの時間もstep_sに含む。1GPUでbatch16/accum1とbatch1/accum16も比較する。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

G固定の分散では各GPUの計算が減るが通信比率が上がる。小モデルではGPU追加が遅くなることもある。大きいmicro batchはGEMM効率を改善しつつactivationを増やす。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. accumを増やすとactivation peakがどう変わるか。
2. Weak scalingでloss曲線をoptimizer stepだけで比べてよいか。
3. Global batchは同じでもbatch16とaccum16の速度が違う理由は何か。
