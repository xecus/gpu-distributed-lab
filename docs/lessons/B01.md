# B01 — Qwen3-8B：DDP / ZeRO-1/2/3全パラメータFine-tuning

GPU：8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

実際の公開モデルQwen/Qwen3-8Bの次トークンlossで全パラメータを更新する。from_pretrainedで公開weightから開始するため、random初期化のPre-trainingではない。LoRAは比較の主実験に含めない。
本native DDPはFP32保持でAdam state込み16P≈128GB＋activationとなりH100 80GBには収まりにくい（H200 141GB/B200 180GBでは収まる可能性がある）。OOMを結果として扱う。ZeRO-1/2/3のどのstate分割で収まるかを測る。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`scripts/part_b.sh / lab/train.py / lab/prepare_data.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。

先に[公開モデル・データ準備](../data_and_real_models.md)を実施する。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。


## 5. 期待結果

DDP OOMは有力な予想。ZeRO-1/2で収まれば、ZeRO-3は常に最速ではない。短いsystems実験では言語性能改善を保証せず、forgettingも確認する。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. OOMはforwardかAdam first stepか。
2. 最も少ない通信で収まるstageはどれか。
3. モデルの最終能力と学習基盤の速度は同じ評価か。
