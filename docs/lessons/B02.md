# B02 — Qwen3-8B：8/16GPU Strong・Weak Scaling

GPU：8／16。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

B01で収まったstageを固定して1node8GPUと2node16GPUを比較する。StrongはG16固定、8GPUのaccum2と16GPUのaccum1。Weakはbatch1/accum2固定、G16→32。
EFAの効果はEFA正常利用をlogで確認した後、Socketを明示した別runで比べる。処理したtoken数、validation loss、コストも速度と共に比べる。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`scripts/part_b.sh / scripts/launch.sh / scripts/scaling.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。

先に[公開モデル・データ準備](../data_and_real_models.md)を実施する。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
export MODE=zero2 TOKENS=$PWD/data/qwen/train.bin
# revisionはB01と同じ8B commit
NNODES=1 ACCUM=2 bash scripts/part_b.sh B02 --out runs/B02/strong8
# 以下は両nodeで実行。NODE_RANK=0/1を設定
export NNODES=2 MASTER_ADDR=REVIEWED_NODE0_PRIVATE_IP RUN_ID=B02-strong16
ACCUM=1 bash scripts/part_b.sh B02 --out runs/B02/strong16
# Weak用はRUN_IDとoutを変え、両nodeでACCUM=2
```

## 4. 測定・CSV

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

Strongで計算が小さくなるとEFA通信が目立つ。Weakは演算を保ちやすいが1updateあたりのtoken/学習統計が変わる。2nodeが割安とは限らない。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. StrongとWeakのefficiency式はなぜ違うか。
2. global batchを固定してもlossのbit一致を要求してよいか。
3. Socket比で速いのに1nodeよりコスト効率が低い状況は何か。
