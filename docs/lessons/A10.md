# A10 — DeepSpeed ZeRO-3

GPU：8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

weight、gradient、optimizerを全て分割する。layer計算前に必要なweightをAllGatherし、計算後に不要な全weightを解放。勾配はReduceScatter。定常stateは16P/D付近だが、実行中layerのweight・activation・prefetch bufferがピークを作る。
実モデルのfrom_pretrained前にHfDeepSpeedConfigを作り保持して、初期読込もZeRO-3対応とする。単なる学習後の分割だけでは初期読込OOMを避けられない。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/train.py / configs/zero3.json`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
NPROC=8 bash scripts/part_a.sh A10 --dim 1024 --layers 12 --seq 512 --batch 1 --accum 2 --steps 100 --profile
NPROC=8 bash scripts/part_a.sh A10 --dim 1024 --layers 12 --seq 512 --batch 1 --accum 2 --steps 150 --resume runs/A10/step_100
```

## 4. 測定・CSV

ZeRO-2と3のpeak VRAM、AllGather頻度、step_s、checkpoint容量/保存wall。resumeは新プロセスで同じtopologyから行う。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

stateメモリはさらに減るがweightのgather通信が増える。小さいモデルではZeRO-2の方が速いことがある。保存とexportには全rankのshardが必要。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. 最も大きい1layerだけがGPUに収まらないとZeRO-3はどうなるか。
2. Prefetchは速度とメモリにどう影響するか。
3. 32Bを8→40GPUへ分割する利点と通信負担は何か。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
