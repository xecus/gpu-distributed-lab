# A13 — マルチノード：EFA・8〜40GPU

GPU：8〜40。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

rank=NODE_RANK×local_world+LOCAL_RANK。rendezvousはprocess group参加者を集める制御通信で、学習tensor通信はNCCL/OFI/EFAが担当する。private TCPが通ってもEFAが動くとは限らない。
ノード内NVSwitchとノード間EFAは帯域/latencyが異なる。torchrunを各ノードで同時に実行し、全worldが同じ設定・サンプル数でcollectiveへ参加する。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`scripts/launch.sh / scripts/efa_env.sh / lab/train.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
source scripts/efa_env.sh
export NNODES=2 NPROC=8 MASTER_ADDR=REVIEWED_NODE0_PRIVATE_IP RUN_ID=A13-efa
# node0では0、node1では1
export NODE_RANK=0
bash scripts/part_a.sh A13 --batch 1 --accum 5 --steps 30 --warmup 5 --out runs/A13/2node
# 同じ全node環境で通信だけを測る
bash scripts/launch.sh lab.collectives --out runs/A13/collectives16.csv --max-power 28
```

## 4. 測定・CSV

8/16/40GPU、G80固定のaccum10/5/2。EFAとSocketのA/B、NET/OFIのログ、all-rank memory、slowest rankを記録。各nodeが独立local volumeなら出力を回収する。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

通信量の大きいDDPではノード間部分が露出しefficiencyが下がりやすい。EFAはSocketより大きなmessageで有利が期待されるが、logで使用を確認する。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. 1node8GPU→5node40GPUで5倍速になる条件は何か。
2. fi_infoは成功なのにNCCLはSocketだった場合、どこを調べるか。
3. 1rankだけデータ読込みが遅いと全体のstepにどう影響するか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
