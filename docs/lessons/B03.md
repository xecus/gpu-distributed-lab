# B03 — Qwen3-32B：ZeRO-3 / FSDP・8〜40GPU

GPU：8〜40。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

32Bの全パラメータ学習はBF16/FP32 Adam state近似512GB、8GPUではstateだけで64GB/GPU。activation、最大layerのgather、optimizerや通信の一時領域でOOMがあり得る。最初はseq256、batch1、activation checkpointingから始める。
ZeRO-3はHF integrationで読込分割、FSDPはrank0 CPU load＋他rank meta＋syncで初期化する。モデル単体を各GPUへ丸ごと置いてから分割する方法は避ける。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/train.py：HfDeepSpeedConfig / Qwen3DecoderLayer FSDP`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。

先に[公開モデル・データ準備](../data_and_real_models.md)を実施する。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
export TOKENS=$PWD/data/qwen/train.bin
export MODEL_REVISION=$(python -c "import json;print(json.load(open('configs/revisions.lock.json'))['Qwen/Qwen3-32B'])")
export NNODES=1 NPROC=8 ACCUM=2
MODE=zero3 bash scripts/part_b.sh B03 --steps 10 --warmup 2 --out runs/B03/zero3-8
MODE=fsdp bash scripts/part_b.sh B03 --steps 10 --warmup 2 --out runs/B03/fsdp-8
# 16/40GPUは同じ手順を両node/全5nodeで実行。Strong G80ならACCUM=10/5/2
```

## 4. 測定・CSV

8/16/40GPUでZeRO3/FSDPをそれぞれ測る。seq256→512は新runへ。全rank peak VRAM、CPU RAM、disk、step_s、NCCL区間、export wall、費用。5nodeは16GPU受け入れ後の追加承認で実行する。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

GPU追加でstate余裕が増え、sequence/batchを増やせる可能性。Strong scalingではparameter AllGatherが露出して効率低下。32Bの長期学習は初回短いrunの後に見積を更新する。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. Stateを5倍分割すればpeakも1/5になるか。
2. FSDP wrap粒度を変えるとpeakとgather回数はどう変わるか。
3. 32Bを40GPUで学習する判断をコスト/精度/メモリで説明できるか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
