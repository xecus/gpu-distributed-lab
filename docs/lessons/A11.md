# A11 — PyTorch FSDP

GPU：8。実行場所：承認済みAWS GPUホスト、リポジトリroot。

## 1. 理論・アルゴリズム

FULL_SHARDのFSDPはunitごとにパラメータを分割し、forward/backwardで必要な重みをgatherする。wrapの粒度はTransformer Block単位。optimizerはwrap後に構築し、分割後のパラメータを参照させる。
QwenではQwen3DecoderLayerをwrapする。大モデル読込はrank0が実重み、他rankはmeta deviceでarchitectureのみ生成し、FSDPのsync_module_statesで初期重みを配布する。FSDP1 APIを使用。

共通の数式・メモリモデル：[theory.md](../theory.md)。

## 2. Pythonコード

実装：`lab/train.py：fsdp / lab/fsdp_export.py`。ブラックボックス化せず、forward・勾配・通信・計測の位置を確認して実行する。
`lab/train.py`の`batch()`、`update()`、`checkpoint()`が学習・測定・保存の共通実装。

## 3. AWS実行コマンド

先に[aws.md](../aws.md)を完了し、`source .venv/bin/activate`。GR00T workerのみ公式uv環境。

```bash
NPROC=8 bash scripts/part_a.sh A11 --dim 1024 --layers 12 --seq 512 --batch 1 --accum 2 --steps 100 --profile
NPROC=8 bash scripts/part_a.sh A11 --dim 1024 --layers 12 --seq 512 --batch 1 --accum 2 --steps 150 --resume runs/A11/step_100
```

## 4. 測定・CSV

ZeRO-3と同じ条件でVRAM、step_s、通信、state precisionを比較。FSDP unitの数とsizeを確認。最初のmodel broadcastをstep計測へ含めない。

[measurement.md](../measurement.md)の定義で記録。`results/experiment_results.csv`に条件・status・実測値を残す。未実行値は空欄。

## 5. 期待結果

定常state分割はZeRO-3に近いが、FP32保持、wrap境界、gather bufferでピークと速度が変わる。LOCAL_STATE_DICTは同じworldでの復元用。

ここは検証前の仮説であり、GPUの実測値ではない。各条件でwarmupを除き、同じ条件を再試行してばらつきを確認する。

## 6. 考察課題

1. rootだけwrapとBlockごとのwrapで何が違うか。
2. optimizerをFSDPの前に作ると何が問題か。
3. FSDP2へ移行するならstate dict/DTensorのどこを変更するか。

成果物：実行command／environment／CSV／失敗log／checkpoint（学習実験）／短い考察。終了時はmonitor停止・全rank保存・instance終了・残存費用確認を行う。
